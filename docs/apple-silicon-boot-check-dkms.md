# DKMS replacements in the Apple Silicon boot check

Installing a DKMS driver is a privileged administrative decision. The boot
verifier recognizes installed DKMS replacements without an additional
Omarchy allowlist. It checks that the resulting installation is consistent,
not that every loaded driver came from the stock kernel package.

For each missing stock module the verifier requires:

- An archived original whose SHA256 matches the installed kernel package's
  mtree, with a DKMS `.origin` record naming the missing path.
- An active, installed DKMS build for that kernel and architecture.
- A replacement selected by `modinfo` from that kernel's module tree, with
  matching kernel vermagic and bytes identical to the active build output.

Each accepted replacement is reported on stderr with the driver/version,
original path and selected replacement path, so update callers that discard
stdout still record the exception. The other boot checks must still pass.

These checks establish consistency with locally installed third-party code.
They do not establish package provenance, verify signatures, review the code
or prove the driver will work. The exception covers missing stock modules
replaced by DKMS, not arbitrary package modifications. Unrecognized or
incomplete DKMS metadata and layouts fail closed. An administrator able to
modify both the build and its installed copy is outside this integrity check's
protection; adding another root-owned allowlist would not change that boundary.

Separately, the verifier allows timestamp, size and checksum differences in
an explicit list of indexes generated by `depmod`, for the installed kernel
only. Ordinary kernel installation regenerates those files. Their content is
not authenticated by the package checksum check. Missing indexes,
ownership/permission changes and changes to kernel-build metadata such as
`modules.order`, `modules.builtin` and `modules.builtin.modinfo` remain failures.
