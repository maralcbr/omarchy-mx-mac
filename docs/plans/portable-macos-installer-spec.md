## Problem Statement

People want to run the Omarchy Mac installer to install Omarchy on disk. The current PKG first installs a Mac application and a persistent privileged helper, adding permanent software and setup steps to a task that should be disposable. This also prevents a straightforward download, open, install, and discard experience.

The desired distribution target is central Homebrew Cask, with a direct download of the same application. Users should not need the Mac App Store, a PKG, a DMG, a manually installed daemon, or developer tools. People who encounter an interrupted installation should be able to reopen the launcher and start over safely.

Current retry behavior does not deliver that last requirement. Existing installation detection and removal recognize complete layouts and reject partial or ambiguous layouts; mutation journals deliberately stop when an operation has an intent record without a completion checkpoint. Merely reopening the current app cannot safely restart every failed installation.

## Solution

Implementation clarification from the owner, 2026-09-10: preserve the existing installer experience exactly, with no new screens. Keep the existing layout, navigation and installation flow. Temporary privilege handling operates behind the existing Install action; interrupted-attempt handling reuses existing review, confirmation and error surfaces. The separate privilege qualification harness is developer tooling and must never appear in the shipping installer or distribution artifacts.

Distribute a Developer ID signed, hardened, notarized and stapled Mac application inside a ZIP. Direct-download users extract the ZIP and open the app from Downloads, without moving it into Applications. The application remains an unprivileged GUI and obtains administrator authorization to launch a temporary privileged worker only when necessary. The worker has a bounded lifetime and leaves no persistent service or login item.

Submit the same application to central Homebrew Cask using normal app installation, followed by an explicit launch. A documented install-and-open command may combine those steps. Executing a disposable GUI directly through Homebrew remains a preference, but ordinary Cask installation is accepted and is the initial solution. Installing or uninstalling the Cask must never itself start an Omarchy disk operation.

Preserve the current hardware eligibility, signed catalog and payload checks, exact-plan review, machine-owner authorization, and Recovery handoff. If execution is interrupted, stop at a safe operation boundary where possible and leave an incomplete attempt. On a subsequent launch, offer a reviewed **Start over** operation for resources demonstrably created by that attempt, then prepare and approve a fresh installation plan. Never guess which partitions are safe to erase.

## User Stories

1. As a person installing Omarchy, I want to download one archive containing the Mac app, so that I can start without running a package installer.
2. As a direct-download user, I want to extract and launch the app from Downloads, so that copying it into Applications is optional.
3. As a direct-download user, I want a ZIP distribution, so that mounting a DMG is unnecessary.
4. As a person installing Omarchy, I want macOS to verify the app normally, so that I do not need to disable Gatekeeper or remove quarantine attributes.
5. As a person installing Omarchy, I want the required execution components bundled with the app, so that I do not need Xcode or a separate Python installation.
6. As a Homebrew user, I want the installer in central Homebrew Cask, so that I can obtain it through my usual package manager.
7. As a Homebrew user, I want clear installation and launch instructions, so that I can reach the installer with minimal steps.
8. As a Homebrew user, I want installing the Cask to place the launcher without touching my disk layout, so that installation begins only after I review and approve it in the app.
9. As a person choosing a release, I want the website and Homebrew to deliver the same qualified app artifact, so that the installation behavior is consistent.
10. As a person installing Omarchy, I want to choose among the existing release channels, so that this packaging change preserves the current channel experience.
11. As a person with an unsupported Mac, I want a clear refusal before privileged work, so that a distribution change does not accidentally broaden hardware support.
12. As a person installing Omarchy, I want to review the exact disk and allocation before authorizing execution, so that I understand the changes being requested.
13. As a person changing an installation plan, I want old approval to become invalid, so that execution cannot use stale consent.
14. As a person installing Omarchy, I want a native administrator authorization flow when privileged work is needed, so that I do not manually install or enable a daemon.
15. As a person cancelling administrator authorization, I want to return to a usable installer without disk changes, so that declining a prompt is safe.
16. As a person supplying machine-owner credentials, I want rejection and retry to remain understandable, so that I can correct an error without restarting disk work.
17. As a person installing Omarchy, I want the GUI to remain unprivileged, so that administrator access is limited to the worker that needs it.
18. As a person installing Omarchy, I want only the authentic app and helper to communicate, so that an unrelated process cannot submit disk operations.
19. As a person with multiple app copies or Mac accounts, I want only one mutating installation operation at a time, so that competing workers cannot change the same disk.
20. As a person encountering a worker startup failure, I want a specific, actionable error, so that I know whether authorization or execution actually began.
21. As a person viewing progress, I want communication failure to preserve the last known installation state, so that the app does not falsely claim that nothing changed.
22. As a person who opens the app but never installs, I want an unused temporary worker to expire, so that it does not remain running indefinitely.
23. As a person completing the Mac stage of installation, I want the temporary worker to exit, so that no ongoing privileged service is left behind.
24. As a person restarting macOS, I want no installer helper to return automatically, so that this one-time task creates no boot service or login item.
25. As a person quitting during installation, I want execution to stop at a safe operation boundary, so that the installer does not deliberately finish the entire install in the background.
26. As a person whose Mac loses power or whose installer crashes, I want the next launch to detect the unfinished attempt, so that I am not led into a blind fresh installation.
27. As a person reopening after interruption, I want to see whether an earlier operation is still active, so that a second attempt cannot overlap it.
28. As a person restarting a failed attempt, I want to review the unfinished resources that Start over will remove, so that cleanup requires informed confirmation.
29. As a person restarting a failed attempt, I want cleanup limited to resources proven to belong to that attempt, so that macOS and unrelated installations remain protected.
30. As a person restarting after macOS was already shrunk, I want the installer to use valid existing free space, so that the old shrink request is not repeated blindly.
31. As a person restarting a failed attempt, I want a freshly inspected and approved installation plan after cleanup, so that it reflects the current disk state.
32. As a person interrupted during Start over, I want the next launch to reconcile the cleanup itself, so that another interruption does not cause arbitrary repeated deletion.
33. As a person with missing or inconsistent attempt records, I want the installer to explain why automatic Start over is blocked, so that uncertainty cannot erase my data.
34. As a person with an existing complete or subsequently used Omarchy installation, I want it excluded from failed-attempt cleanup, so that ordinary reuse cannot erase an installed system.
35. As a person who declines Start over, I want the unfinished attempt left unchanged, so that inspecting it does not itself authorize cleanup.
36. As a person completing installation, I want the existing Recovery instructions and handoff to remain available, so that I can finish the Apple Silicon boot setup.
37. As a person retrying Recovery authorization, I want that retry to avoid repeating partition or payload work, so that the existing narrow retry remains safe.
38. As a person who finishes installing Omarchy, I want to discard the downloaded Mac launcher, so that Omarchy does not depend on keeping it.
39. As a Homebrew user, I want uninstalling the Cask to remove the Mac launcher without removing Omarchy or essential attempt evidence, so that software housekeeping does not become disk cleanup.
40. As an Omarchy user, I want the Mac launcher to add no ongoing update service, so that it remains a one-time installer.
41. As an Omarchy user, I want the existing Linux update system left unchanged, so that removing the Mac launcher does not change installed-system updates.
42. As a person with an old package-installed helper, I want an incompatible active worker detected before new disk work, so that legacy and temporary helpers cannot mutate concurrently.
43. As a release maintainer, I want immutable ZIPs with checksums of the final stapled app archive, so that consumers can verify the bytes actually distributed.
44. As a release maintainer, I want direct downloads to be releasable before central Cask acceptance, so that upstream review does not prevent a qualified website release.
45. As a maintainer, I want the deprecated privilege mechanism isolated behind one adapter and qualified first, so that a platform incompatibility is discovered before integrating disk changes.
46. As a maintainer, I want existing session, trusted-execution and engine test interfaces reused, so that tests verify behavior without creating parallel implementations of the installer.
47. As a maintainer qualifying a release, I want proof from the exact downloadable artifact through Recovery and an interrupted attempt, so that a successful source build is not mistaken for installation readiness.

## Implementation Decisions

1. **Distribution contract.** Replace the current PKG requirement with a portable app in a ZIP. Developer ID signing, hardened runtime, notarization and app stapling remain required for public distribution. Produce the final ZIP after stapling and calculate its checksum afterward. Apple documents that ZIP archives cannot themselves be stapled. [Apple notarization workflow](https://developer.apple.com/documentation/security/customizing-the-notarization-workflow)
2. **Homebrew contract.** Target central Homebrew Cask with the ordinary app artifact, immutable versioned download, checksum and canonical homepage. The Cask places the app; launching and approving disk installation remain explicit user actions. Do not add an installer script that starts Omarchy installation during Cask installation. Homebrew's formula-oriented `exec` command does not provide the desired temporary GUI-Cask execution flow. [Cask Cookbook](https://docs.brew.sh/Cask-Cookbook), [Homebrew manual](https://docs.brew.sh/Manpage)
3. **Portable resources.** Resolve the helper and bundled engine relative to the running application, without assuming an Applications location. Any required privileged staging must preserve the existing verified artifact and root-owned import boundaries. Qualify a real browser download with quarantine intact, including resource access under app translocation where applicable; do not strip quarantine as a workaround.
4. **Privilege adapter.** Use Authorization Services and `SMJobSubmit` as the initial temporary-worker mechanism. The user explicitly accepts deprecation for this release. Apple DTS identifies this mechanism as an option for one-shot privileges in a widely distributed product. Isolate its platform-specific behavior so it can be replaced later without changing the install engine contract. Do not replace it with an installed helper or a root GUI. [Apple DTS guidance](https://developer.apple.com/forums/thread/708765)
5. **Qualification gate.** Before integrating disk execution, demonstrate a harmless authenticated request from the intended signed and notarized downloaded app to a temporary worker, with administrator cancellation, startup failure and worker retirement covered. If this mechanism cannot satisfy the supported-platform requirements, report measured failure and alternatives; do not silently change the agreed architecture.
6. **Session lifecycle.** Replace package-presence-based readiness with an authenticated temporary-worker lifecycle that distinguishes not started, authorizing, starting, ready, executing, stopping, exited and failed outcomes. Define startup and idle timeouts. A health check, rejected credential, or removal preview does not complete the whole session. Keep the worker available for the bounded request sequence, then retire it when finished or safely stopped.
7. **Privilege persistence.** Do not install a system launch daemon plist, a persistent privileged-helper executable, an installer login item or an ongoing updater. Temporary job removal and process exit must be observable. Retain only installation evidence needed for diagnostics or safe Start over; disposable worker files are separate from that evidence.
8. **IPC and identity.** Preserve mutual app/helper signing requirements, exact-plan validation, payload verification and credential clearing. Separate the helper's code-signing identity from its runtime service address. Prefer one fixed transient address distinct from the legacy helper for simplicity, subject to the capability proof. Authenticate the peer and verify protocol compatibility and active state before trusting its readiness.
9. **Machine-wide serialization.** Extend the existing per-user app lease and per-process helper execution guard with a machine-wide mutation boundary. Two copies, two users, replacement helpers, and surviving engine child processes must not produce concurrent mutators. A dropped UI connection or an unlocked per-user lease is not evidence that earlier disk work has ended.
10. **Authorization semantics.** Native administrator authorization and machine-owner credentials needed for the current engine and Recovery flow remain distinct. Do not promise a single total password prompt. Denying authorization or supplying rejected credentials must not start a disk operation or discard a valid reviewed plan unnecessarily.
11. **Attempt evidence.** Before the first disk mutation, persist a protected root-owned attempt record binding an attempt identifier to disk identity, protected macOS and Apple recovery identities, the original partition inventory, the approved target extent and plan identity. Extend the engine journal with durable intent and observed results around individual partition-changing operations, including stable partition/container identities. The existing coarse completion checkpoints are insufficient by themselves.
12. **Stop contract.** A normal quit requests a stop at an operation boundary. The engine must not begin another mutation after acknowledging that stop. UI loss, worker failure and system interruption leave an unfinished attempt that must be reconciled before another operation starts. An in-flight APFS operation cannot be promised an immediate safe abort, and the app must not present interruption as successful rollback.
13. **Start over contract.** Inspect unfinished-attempt evidence before normal planning. Establish that no earlier mutator remains, reconcile recorded ownership with the current disk, present the cleanup extent for confirmation, then remove only resources attributable to the failed attempt. Reinspect, prepare a fresh plan, and obtain fresh approval before installing again. Reuse already freed space when valid instead of replaying an old shrink command.
14. **Interrupted cleanup.** Journal cleanup intent and results so that Start over is itself restartable. Missing or corrupt records, changed identities, unexpected partitions, an unhealthy APFS state, an active operation, or evidence of a subsequently used installation must block automatic cleanup with a specific explanation. Partition labels, approximate locations and stale failure flags are insufficient proof of ownership.
15. **Existing installations and Recovery.** Preserve the existing refusal to replace a complete installation and the separate reviewed Omarchy removal feature. A completed stage-one handoff must not be treated as a failed partial installation simply because Recovery has not yet finished. Preserve the narrow Recovery-authorization retry without replaying disk work. The target's Recovery handoff resources remain independent of the disposable downloaded launcher.
16. **Legacy compatibility.** Do not implement PKG migration or legacy-helper cleanup in the app. Detect an incompatible active legacy helper and prevent concurrent privileged disk work. Do not unload or delete another installer installation automatically.
17. **Release integration.** Update app packaging, artifact validators, release metadata, download links and channel publishing to consume the new ZIP format. Any changed engine source must be rebuilt into the immutable execution archive and repinned through the normal engine release process; source changes alone do not update the engine delivered to users. Preserve current supported models, channels and minimum macOS policy unless a separately approved change requires otherwise.
18. **Delivery order.** Qualify temporary privileges first, integrate bounded worker lifecycle and serialization second, implement attempt ownership and Start over third, complete portable UI and ZIP packaging fourth, qualify the exact artifact on supported hardware fifth, and publish the website artifact and submit central Cask sixth. Keep central maintainer acceptance distinct from submission and website availability.

## Testing Decisions

1. **Test observable behavior.** A good test exercises user intent at a public module boundary and asserts the resulting state, allowed disk effects, transcript or artifact. Do not test private method ordering, mirror implementation logic, or mock away the trust checks whose behavior is under test.
2. **Primary seam: installer session.** Reuse the existing installer session/environment interface as the highest application seam. Exercise inspect, plan, review, approve, authorize, execute, stop, reopen and Start over through that interface. The user explicitly confirmed these existing boundaries and the small real signed-app check. Existing InstallerSessionTests and InstallerSimulationTests provide prior art for state transitions, changed approvals, authorization rejection, progress, communication failure, existing-install refusal and Recovery retry. Extend their scenarios rather than introducing a second workflow model.
3. **Existing execution seam.** Reuse the trusted execution submission boundary and stage-one engine adapter for effects that cannot be proven through a simulated UI. ClosedEngineHelperServerTests already test accepted packages, rejected credentials, substituted plans, invalid transcripts and unsupported devices. AuthenticatedEngineXPCSubmitterTests, handoff import tests and pinned-executor tests provide prior art for trusted IPC and artifact validation. Stage1CoordinatorTests provide prior art for mutation intent, checkpoint validation and Recovery-only retry. Keep failure injection at these existing boundaries rather than mocking every internal operation.
4. **Privilege and lifetime coverage.** Assert native authorization cancellation produces no disk work; startup timeout and incompatible peers fail clearly; unused workers expire; the worker survives harmless checks and credential retry; completion and safe stop retire it; reboot does not restore it. Exercise simultaneous app copies and users, an active legacy worker, UI disconnection and surviving child processes to prove machine-wide exclusion.
5. **Restart coverage.** Inject interruption before and after each partition mutation boundary and during cleanup. Check the next launch's externally visible classification and the actual recorded disk effects: no deletion of protected or pre-existing partitions, no second blind macOS shrink, no stale-plan execution, and no overlap with another mutator. Cover incomplete/corrupt evidence, externally changed layouts, completed stage-one handoffs, completed installations, subsequently used systems, and declined cleanup confirmation. Use disposable disk fixtures and the real journal parser before physical testing.
6. **Real platform check.** Pure tests cannot establish Gatekeeper, code-signature, authorization or launchd behavior. Use one small integration harness that launches the actual signed app extracted from a browser-downloaded ZIP, performs a harmless authenticated worker request and proves retirement without disk writes. Cover the supported macOS floor and current supported macOS release, with quarantine intact and an ordinary user-owned download location. Expand the platform matrix only for a demonstrated compatibility concern.
7. **Packaging and release evidence.** Verify bundle structure, embedded components, reciprocal signing requirements, notarization and stapling, final ZIP checksum, and immutable download metadata. Reuse existing packaging and channel-publication tests for artifact handling. Exercise Cask installation, explicit launch and uninstallation; confirm no disk operation occurs as a Cask lifecycle side effect and no essential attempt evidence is erased.
8. **Focused completion checks.** Run focused Python engine tests and syntax checks, Swift tests in debug and release through the project's macOS tooling, strict Swift formatting, applicable packaging checks and unsupported-host refusal. After UI changes, rebuild and open one review app and inspect the fresh, denied, interrupted, Start over, blocked and Recovery states. Do not rerun an unchanged broad suite merely to accumulate passes.
9. **Physical acceptance.** Use an exact immutable candidate on supported, authorized test hardware for a complete installation through Recovery and a controlled interrupted attempt followed by Start over. Record original protected disk identities, actual resulting layout, macOS access and successful Omarchy boot. Reuse proof for the same candidate and environment; a source build, simulation or root launch alone is not physical installation proof.

## Out of Scope

- Mac App Store distribution, a required DMG, PKG-based installation, or requiring direct-download users to move the app into Applications.
- A persistent privileged daemon, login item, Mac self-updater, or automatic background completion of an interrupted installation.
- Changes to Omarchy Linux updates, general m1n1/initramfs repair, new disk-encryption/offline-install features, or expanded model support.
- A custom Homebrew execution framework, custom tap as the final distribution target, or disk installation triggered by Cask installation.
- General-purpose automatic rollback, automatic deletion of existing Omarchy installations, arbitrary partition repair, or guessing ownership when attempt provenance is insufficient.
- Replacing the existing explicit removal feature with broad automated cleanup.
- In-product migration or removal of helpers left by old PKG installations.
- Removing the target's Recovery handoff app or requiring the downloaded launcher to remain after the handoff.
- Rewriting unrelated installer UI, trust infrastructure or engine behavior merely as part of the packaging change.
- Performing production signing, physical installation, release publication or central Cask submission as part of writing this specification. Those remain implementation and qualification steps under the applicable owner authority.
